# 设计审查方法

本文件只负责范围、证据与报告编排。数值标准以 [standards.md](standards.md) 为准，专项细节由对应模块维护；不要再次加载整套资料。

## 1. 确定任务与基线

“看看、审查、建议”默认只读；“审查并修复、打磨、优化”在既有范围内包含实现授权。只读报告默认在对话交付；用户请求保存或导出才写报告文件。产出约定见 [execution.md](execution.md)。

先读取明确指定的对象、目标用户、核心任务、项目 token 和品牌说明。仅在缺失信息会改变审查范围或判断基线时提问。没有声明设计流派时以项目目标和一致性为基线。

## 2. 深度与覆盖

- **快速**：检查指定组件或页面的关键风险，不强制五项分数或完整专项清单。
- **深度**：检查目标范围的五维与相关专项，分开记录已验证和未验证项。
- **全项目 / 全流程**：先枚举路由、页面模板、关键状态和用户旅程，再逐项检查；必须列出覆盖记录，不能用首页代表全站。
- **专项**：直接进入匹配模块，不额外做全套五维审查。

## 3. 页面与状态取证

1. 从路由配置、入口、导航和用户材料发现页面，避免无边界爬取。
2. 记录每页或模板的关键任务、入口、成功、空态、错误、加载和权限状态，按实际适用性选择。
3. 使用可用工具验证目标视口、键盘与关键操作；代码和截图也可支持有限结论。
4. 共享组件可以复用结论，但检查代表性调用场景，并披露抽样覆盖。无法进入的登录页、动态路由和数据状态标“未验证”。
5. 跨页检查导航、组件、术语、颜色、排版、状态与布局一致性。

运行观察、截图观察、静态推断分别记录。仅在判断依赖外部产品、版本、规范或资产事实时查证相关来源；不因页面出现品牌名就强制查询其最新发布信息。无法联网时不编造事实，也不把外部研究说成已完成。参考流程见 [integration.md](integration.md)。

## 4. 五维与专项

五维评分读取 [standards.md](standards.md) §1–3；无证据的维度标未验证。专项按请求或发现选择：

- [AI 痕迹](../skills/04-review/ai-slop-check/SKILL.md)：模板与真实任务冲突。
- [无障碍](../skills/04-review/accessibility-audit/SKILL.md)：语义、对比、键盘、表单、动效。
- [层级节奏](../skills/04-review/hierarchy-rhythm-review/SKILL.md)：视觉顺序与一致性。
- [交互状态](../skills/04-review/interaction-states-pass/SKILL.md)：适用状态、反馈、恢复。
- [交付前质量检查](../skills/04-review/polish-pass/SKILL.md)：明确需要综合检查时编排四个面。

不把综合模块再嵌入每个专项，避免重复检查与递归委派。

## 5. 整理发现

按共享 P0–P3 分级，优先用户影响。每条写明位置、证据、实际问题、建议和验收条件。同一根因合并，保留不同的受影响位置。

例如“提交失败后按钮仍禁用，无法重试；在请求 finally 恢复可操作状态，保留输入并显示关联错误；验收：失败后可再次提交”。不要只写“交互不够好”。

分开列出已确认缺陷、待验证风险、可选审美建议。样式关键字命中不直接算缺陷，不能凭缺失工具推断页面失败。第三方限制可能真实影响用户，应说明责任范围和可选缓解。

## 6. 自检与交付

- 每个发现有证据和用户影响，分数与描述一致。
- 高分有反证检查，低分也有依据，不强行制造缺陷。
- 修复建议使用真实存在的 token/组件，或明确是新增建议。
- 不把截图评价扩展成键盘或端到端验证，不把抽样扩展成全覆盖。
- 先列严重发现，再给评分（需要时）、保留项、覆盖与限制、简短结论。

## 7. 修复交接

用户已要求修复时，将已确认发现交给 [design-improve](../skills/05-improve/design-improve/SKILL.md)，无需重复索要授权。复核旧报告位置后实施，修后只重验相关项与受影响调用方。

只有明确要求评分对比且证据范围可比时才重评五维。通过编译不等于视觉通过，分数上涨不等于问题解决。
