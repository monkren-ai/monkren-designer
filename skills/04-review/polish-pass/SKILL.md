# 交付前质量检查

## 1. 范围与模式

依据用户请求确定目标页面、组件、平台和交付标准。“检查能否交付”只报告；“帮我打磨这页”包含范围内修复授权，无需要求用户追加固定措辞。

结构尚未稳定时先指出影响交付的结构问题，继续完成适用检查；不因存在占位内容而强制停止。

## 2. 四个检查面

这是显式的综合编排，按需读取以下模块，允许覆盖四个检查面；不重复启动每个模块自己的编排：

- [无障碍](../accessibility-audit/SKILL.md)：语义、键盘、对比度、表单与目标区域。
- [AI 痕迹](../ai-slop-check/SKILL.md)：脱离品牌与任务的模板、装饰和虚构内容。
- [层级节奏](../hierarchy-rhythm-review/SKILL.md)：信息顺序、阅读流和组件一致性。
- [交互状态](../interaction-states-pass/SKILL.md)：适用状态、动作反馈与恢复路径。

默认由当前 agent 顺序完成。只有环境允许且范围足以受益时才可并行委派，子任务均只读、共用范围与证据格式，不再递归委派。没有子 agent 不影响完成。

## 3. 聚合与处置

合并重复发现，使用 [共享分级](../../../references/standards.md) §4。区分已确认缺陷、待验证风险和可选风格建议；第三方限制仍可能影响交付，不能自动当作误报。

只读任务交付发现即可。已授权修改时修复确定问题；常规可逆选择沿用设计系统。改变核心品牌、产品范围或存在阻断性取舍时，才交给用户决策或读取 advisor。

## 4. 复验与结论

检查受影响视图、关键流程、焦点、对比度和响应式回归。结论须匹配覆盖面：通过已检查范围、存在阻断问题，或因缺少运行条件尚不能确认。

汇报发现与已修复事项、实际验证、未决项。没有浏览器或交互证据时不宣称“可以发布”或“WCAG 合规”。
