# 建立美学方向

先检查项目 token、组件、品牌资料和用户指定参考。有可用体系就延展它；只有用户要求更换方向时才提出替代。

## 1. 从产品目标作选择

从 brief 提取受众、核心任务、信息密度、平台、期望语气和不能改变的约束。信息足够时直接提出有理由的方向；影响核心选择的缺口才提问。

未指定风格时给出一个推荐。用户希望比较时默认提供三个实质不同的方向，数量服从用户要求。区别应来自构图、排版、密度或交互策略，不只换强调色。

## 2. 把方向落到系统

- **字体**：具体字族、字重、字号层级、行高与 fallback；检查中文等目标语言的字形覆盖和资产可用性。系统字体和常见字体都可使用，不为新颖而替换。
- **色彩**：品牌、文字、背景、边界和必要语义色的角色；验证实际前景与背景对比度。沿用项目颜色格式，OKLCH 是可选工具，不保证色彩天然可访问。纯黑白可以是有意的品牌选择。
- **密度与布局**：按内容任务选择紧凑或宽松，说明网格、阅读宽度和响应式行为。
- **形状与组件**：统一圆角、边框、阴影、按钮层级及适用状态，避免每个区块重新发明样式。
- **图像**：使用已有真实资产；缺失时明确占位。不把图像格式本身当成质量判断。
- **动效**：说明其反馈或空间关系目的；安静、即时反馈同样有效，尊重 reduced-motion。

用具体决定解释“现代”“高级”等形容词，但不强迫所有项目采用同一种排版或色温。

## 3. 按请求交付

只要建议时，在对话中给出方向、关键 token、理由和未决项，不写项目文件。用户要求实现时，将必要决策记录到项目已有设计文档或源码旁，并用最小相关界面验证后继续实现。

设计说明放在交付说明或设计文档中；除非用户要求展示设计系统，不在产品界面插入“design system summary”、风格标签或实现说明。

## 4. 验证

检查代表性桌面与移动布局、字体实际加载、内容溢出、颜色对比和交互状态。工具不足时说明未验证项。常规可逆选择自主完成；只对会改变用户目标或范围的决定请求澄清。
